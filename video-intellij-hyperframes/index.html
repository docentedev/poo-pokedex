CAPÍTULO 02 · MODULE-INFO
EL ERROR QUE A TODOS NOS PASA

Módulos: requires, opens y exports

Run · PokedexCartas
Exception in Application start method
Caused by: java.lang.IllegalAccessException:
module cl.duoc.pokedex does not
"opens cl.duoc.pokedex.controller"
to module javafx.fxml
at javafx.fxml.FXMLLoader…
¿Por qué pasa?
1

FXML no hace new PokedexController(): lo crea por reflexión.

2

La reflexión necesita un permiso explícito del módulo.

3

Ese permiso se escribe en module-info.java con opens.

module-info.java JAVA
1module cl.duoc.pokedex {
2 requires javafx.controls;
3 requires javafx.fxml;
4 requires com.google.gson;
5
6 opens cl.duoc.pokedex.controller
7 to javafx.fxml;
8
9 opens cl.duoc.pokedex.model
10 to com.google.gson;
11
12 exports cl.duoc.pokedex;
13}
Qué significa cada línea
requires

Mi módulo necesita este otro módulo.

opens … to

Permite reflexión, solo al módulo indicado.

exports

Hace público un paquete para otros módulos.

Abre solo lo necesario: no todo el proyecto.
opens no es lo mismo que exports
DirectivaQué permiteCuándo usarla
requires Usar otro módulo. JavaFX, FXML, Gson.
opens … to Acceso por reflexión. FXML → controlador · Gson → modelo.
exports Acceso público normal. Cuando otro módulo importa tus clases.
Regla práctica

¿La clase se carga desde FXML? → opens … to javafx.fxml

¿Gson lee o escribe el modelo? → opens … to com.google.gson

¿Solo lo usa tu app? → no necesitas exports.

Este es el error más común al empezar: el módulo no abre el paquete del controlador a javafx.fxml.

FXML crea el controlador por reflexión; sin opens, la JVM bloquea el acceso.

requires declara lo que necesitas; opens … to autoriza la reflexión; exports publica un paquete.

Abre solo lo necesario: el controlador a javafx.fxml y el modelo a Gson.

exports no reemplaza a opens: uno publica clases, el otro permite reflexión.

Si el error menciona un paquete, abre ese paquete al módulo que lo pide.

CAPÍTULO 04 · INICIALIZACIÓN
ATRIBUTO · CONSTRUCTOR · initialize()

¿Quién crea cada objeto y cuándo?

1
Se crea el controlador new PokedexController()

FXMLLoader instancia la clase. Los campos @FXML todavía valen null.

2
FXML crea los controles <ComboBox fx:id="categoriaComboBox"/>

El loader lee el archivo y construye cada control del layout.

3
Inyección de campos categoriaComboBox = <el ComboBox creado>

Por reflexión, JavaFX asigna cada control al campo con el mismo fx:id.

4
JavaFX llama initialize() initialize() → setItems(...)

Los campos ya existen: aquí se configuran. Después se muestra la ventana.

El campo cambia de estado
categoriaComboBox null
categoriaComboBox ComboBox@1a2b
categoriaComboBox 3 opciones · listo

Si tocas el campo antes del paso 3: NullPointerException.

✗

El constructor corre antes de que FXML inyecte los campos.

✗

categoriaComboBox todavía es null: cualquier llamada falla.

✓

initialize() corre después de inyectar y antes de mostrar la ventana.

Regla de oro: cada cosa en su lugar
Dónde Qué va ahí Por qué
Atributo Declarar los @FXML; listas con new. FXML llena los @FXML; las listas existen desde el inicio.
Constructor Dependencias que no son de la vista. Corre antes de la inyección: no toques controles.
initialize() Items, columnas, selección, listeners. Corre después de inyectar y antes de mostrar.
onAction Reaccionar al clic del usuario. La ventana ya está visible y los datos cargados.

Si el FXML tiene fx:id, no lo crees con new: el objeto lo crea el FXML.

FXMLLoader crea el controlador, crea los controles y los inyecta: todo antes de initialize().

Por eso el constructor no sirve para tocar un ComboBox: en ese momento el campo todavía es null.

El atributo declara el control; initialize() lo configura: opciones y selección.

initialize() se ejecuta una vez, después de la inyección y antes de que aparezca la ventana.

La TableView también se declara como campo y se arma en initialize(): columnas, factories y datos.

Cada columna es un campo @FXML con su fx:id: si no coincide, la columna queda en null.

Atributo: declara. Constructor: dependencias. initialize(): configura. onAction: reacciona.

CAPÍTULO 05 · CAPAS
PATRÓN DE CAPAS

Cada pieza con una sola responsabilidad

1
App / Launcherarranque
HACE

Arranca JavaFX y carga el FXML.

NO HACE

Lógica de negocio.

2
Vistapokedex-view.fxml
HACE

Declara controles, layout y eventos.

NO HACE

Validar ni guardar datos.

3
ControladorPokedexController
HACE

Recibe eventos, valida y actualiza la tabla.

NO HACE

Leer o escribir archivos.

4
ModeloCarta · CartaPokemon · CartaEnergia
HACE

Datos, reglas y calcularValorEstimado().

NO HACE

Conocer JavaFX o JSON.

5
Repository + DAOmemoria · Gson · JSON
HACE

Colección en memoria y persistencia con Gson.

NO HACE

Mostrar mensajes ni tocar la vista.

DEPENDENCIAS
Vista
→
Controlador
→
Modelo / Repository
→
DAO
→
JSON

Cada capa tiene una sola responsabilidad: si una hace dos cosas, algo está mal ubicado.

La vista declara; el controlador coordina; el modelo decide; el repository y el DAO guardan.

El controlador nunca lee archivos: delega en Repository, que usa el DAO con Gson.

El modelo no conoce JavaFX: por eso se puede probar y reutilizar sin la interfaz.

CAPÍTULO 07 · ERRORES
DIAGNÓSTICO RÁPIDO

Seis errores, seis salidas

01EJECUTAR
JavaFX runtime components are missing

Causa: ejecutar sin el plugin o sin módulo.

Fix: usa mvn javafx:run.

02MÓDULO
does not "opens … to module javafx.fxml"

Causa: falta abrir el paquete del controlador.

Fix: opens …controller to javafx.fxml;

03EVENTO
Controller method not found

Causa: onAction no coincide o falta @FXML.

Fix: iguala el nombre y anota el método.

04NULL
NullPointerException en initialize()

Causa: el fx:id no coincide con el campo.

Fix: mismo nombre en FXML y en Java.

05RUTA
Location is not set

Causa: la ruta del FXML no existe.

Fix: getResource("/cl/duoc/…/pokedex-view.fxml")

06GSON
Cannot access field / JSON inválido

Causa: falta opens del modelo o JSON corrupto.

Fix: abre model a Gson y valida el JSON.

Lee la primera línea del error: casi siempre dice el módulo o el nombre que no coincide.

«JavaFX runtime components are missing» se arregla ejecutando con mvn javafx:run.

Si el error nombra un paquete y un módulo, agrega el opens correspondiente.

Un NullPointerException en initialize casi siempre es un fx:id mal escrito.
